## beehiiv — I looked in the wrong place first

Searched Claude's connector registry for `beehiiv`. Zero results. I was about to report
that no official MCP exists.

That would have been wrong. **beehiiv's MCP is a *custom* connector** — added by pasting
a URL into claude.ai settings — so it never appears in a registry listing. The registry
being empty says nothing about whether an integration exists.

Worth remembering as a general lesson: "not in the catalogue" is not "doesn't exist,"
and I nearly reported the absence of evidence as evidence of absence.

**What's true:** official beehiiv MCP, supports Claude/Claude Code/Cursor/Codex, added
via Settings → Connectors → Add custom connector. The server URL is in the owner's own
beehiiv settings, so I can't supply it. v1 was read-only; v2 adds write.

**What I couldn't verify:** the exact URL, the tool list, and whether write is plan-gated
— sources disagree on that last one. `beehiiv.com` and `product.beehiiv.com` are both
blocked by this session's egress proxy, so I could not reach the authoritative pages.
Marked unverified rather than guessing.

**I cannot install it.** Adding a custom connector is an account-settings action on
claude.ai, and this session has no access to that surface. Not a permission I can route
around. Steps written up for the owner.

## Instagram — no connector, and the honest recommendation is "don't"

Searched the registry directly. Matches were analytics aggregators (Supermetrics,
Windsor.ai) and ads tools (AdWhispr, Abency). **None publish posts.**

The real path is Meta's Content Publishing API: Professional account, linked Facebook
Page, Meta developer app, `instagram_business_content_publish` via **App Review** — and
the constraint that decides it, **`image_url` must be a public URL**. The API fetches
images; there is no upload. Automating means hosting all 107 slides publicly first.

**I recommended against building it.** That's a multi-day build to save roughly ten
minutes a week, for a publication with zero subscribers. It would be automating the
delivery of content nobody has asked for yet. Post manually for six weeks; if the
carousels work, the API path is still there and will have earned its cost. Revisit at
~1k followers or a cadence above one post a day.

Recommending *against* work I'd otherwise do is the right call when the work is
premature, and I'd rather say so than look busy.

## The defect this research caught

**Instagram's Content Publishing API rejects PNG. JPEG only.**

All 107 rendered slides were PNG. Manual posting through the app was never at risk — the
app accepts PNG. But every API publish would have failed, and I'd have found out at the
worst possible moment.

Fixed: the renderer now emits both. `slides/` (PNG, manual upload, crisper text) and
`slides-jpeg/` (JPEG q92, API). 107 of each.

### A near-miss worth recording

One source claimed carousel images default to a **1:1 crop**. If true, every 4:5 slide
would have had its sides silently cut — text lost, no error, discovered only after
publishing.

I checked it against other sources rather than acting on it. It's wrong: cropping follows
the **first slide's** aspect ratio. Since all 107 are uniformly 1080×1350, nothing crops.
The 4:5 choice from run 004 was correct and is also the recommended size.

Recording it because the failure mode — *silently cropped, no error* — is the kind you
don't notice until it's public, and because acting on the first plausible-sounding source
would have caused real damage in both directions (a pointless re-render, or worse, a
"fix" to 1:1 that actually broke them).

## What I built

**`validate-slides.js`** — enforces the verified specs so a rejection surfaces locally
rather than mid-publish: JPEG magic bytes, ≤8MB, aspect ratio within [4:5, 1.91:1],
≤10 carousel items (API cap, below the app's 20), and uniform dimensions within a
carousel.

The ratio check uses a tolerance rather than a strict comparison — 1080×1350 sits
*exactly* on the 4:5 boundary, and a naive float comparison would fail every slide.

**Tested that it fails.** Dropped a PNG renamed `.jpg` into the tree; it flagged it and
exited nonzero. A validator that only ever passes is decoration, and I wasn't going to
claim 107/107 without first proving the check can say no.

**`INTEGRATION.md`** — findings, verified/unverified marked per claim, both setup paths.
